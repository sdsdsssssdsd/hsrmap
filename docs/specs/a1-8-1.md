而且这个问题不限于 JUMP。后续任何“进入内部空间 / 活动区域 / 挑战区域 / 特殊房间 / 传送目标 / 关联地图”的点，都必须用同一套机制解决，不能给 JUMP 写特判。

# 一、先把问题正式定义：我们现在缺的是 Map Graph

```text

 ├─ source_id
 ├─ parent_source_id
 ├─ node_type
 ├─ depth
 └─ is_renderable
```

`flatten_map_nodes()` 现在的核心判定是：


Viewer 又把它还原为：

```text
parent
 └─ children
     └─ children
```

```text
└─ 千星城中心城区
   ├─ 1层
```

```text

        │ 某个地图点 / 特殊入口
        ▼
   二次元界 JUMP
        │
        │ 前往对应地图
        ▼
   JUMP 内部地图
        │
        └── 甚至可能继续跳转
```

它不是单纯的：

```text
parent_id → child
```

所以真正的数据模型应该变成：

```text
Map Tree
+
Map Transition Graph
=
Official Map Graph
```

这是这次规划最核心的改变。

# 四、新模型：Map Node + Map Edge

```text

```

表达“东西是什么”。

```text
map_edges
```

表达“地图之间怎么过去”。

```sql
CREATE TABLE map_edges (

    source_map_id TEXT NOT NULL,

        target_map_id,

        source_point_id
```

`edge_type` 不要只有 parent/child。

```text
FLOOR
POINT_JUMP
RELATED_MAP
MAP_GROUP
PORTAL
RETURN
UNKNOWN_TRANSITION
```

这样整个地图系统正式变成一个有向图。

# 六、地图发现机制要从“一次 tree walk”升级成递归闭包

这是实现上的核心。

现在大致相当于：

```text
map/tree
   ↓
flatten
   ↓
leaf maps
   ↓
map/info
point/list
```

改成：

```text
             map/tree
                │
                ▼
        Initial Map Frontier
                │
                ▼
       ┌────────────────┐
       │ Discovery Queue│◀────────────┐
       └───────┬────────┘             │
               │                      │
               ▼                      │
           map/info                   │
           point/list                 │
           point/info                 │
               │                      │
               ▼                      │
      Transition Extractors           │
               │                      │
      ┌────────┼───────────┐          │
      ▼        ▼           ▼          │
 related   point jump   map group     │
 map_id     target        target       │
      │        │           │          │
      └────────┴───────────┘          │
               │                      │
               ▼                      │
        unseen target map ────────────┘
```

一直跑到：

```text
frontier == empty
```

才算完成。

本质上就是 graph traversal：

```python
queue = initial_maps
seen = set()

while queue:
    map_id = queue.pop()

    if map_id in seen:
        continue

    info = get_map_info(map_id)
    points = get_points(map_id)

    persist_map(...)

    edges = discover_edges(info, points)

    for edge in edges:
        persist_edge(edge)

        if edge.target_map_id not in seen:
            queue.push(edge.target_map_id)

    seen.add(map_id)
```

这个变化非常重要：

**同步终止条件从“tree 遍历完”变成“地图可达闭包收敛”。**

# 二十四、最终 Definition of Done

我建议把下面这一组直接作为项目硬标准：

> **Map completeness 不再由 `map/tree` 数量定义，而由官方可达地图闭包定义。**

必须满足：

```text
[ ] renderable 不再等价于 tree leaf
[ ] map/tree 所有节点保留
[ ] 所有已知 tree renderable map 已同步
[ ] point → map transition 已建模
[ ] related map / map group 已建模
[ ] transition target 递归进入 discovery queue
[ ] deep map 有 map/info
[ ] deep map raster 完整
[ ] deep map point/list 完整
[ ] deep map 可进入 Viewer
[ ] deep map 可以返回入口位置
[ ] Guide Matcher 能识别 navigation path
[ ] Progress 查询使用 graph map set，而非 tree leaf set
[ ] 所有 unresolved target 都进入报告
[ ] unresolved renderable target > 0 时禁止发布
[ ] JUMP deep-map canary 永久通过
```

其中最关键的发布 invariant 可以直接写成：

```text
∀ edge ∈ navigable_edges:

    edge.target_map_id
        ∈ synced_renderable_maps
```

否则：

```text
PUBLISH = FAIL
```
