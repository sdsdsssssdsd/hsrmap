可以，而且我建议把“语言化”明确排除在这一轮之外：**不改 `SOLUTION_PATTERNS` 的多语言能力，其他你列出的卫生问题全部纳入。**

我看了你上传的 `submit.zip`。现在最适合做的不是一次“大重构”，而是一次**保持判定语义不变的工程收口**：把现在已经很强的证据/判定能力，从“项目作者知道该怎么跑”升级为“仓库自己知道该怎么跑、怎么证明、怎么发布、怎么失败”。

# 四、P0：先堵住继续产生工程债的入口

这部分必须先于“大扫除”。

### 1. CLI 入口修正

`hsrmap/cli.py` 末尾直接加入正式模块入口：

```python
if __name__ == "__main__":
    raise SystemExit(main())
```

然后增加真正的 subprocess smoke，而不是再直接调用 `main()`：

```text
python -m hsrmap --help       => rc 0 + 非空输出
python -m hsrmap.cli --help   => rc 0 + 非空输出
```

更重要的是统一命令契约：

```text
0 = 成功，包括明确的 NOOP
1 = 执行/环境/数据错误
2 = publish/review gate 阻断
```

所有成功的 command 必须打印最终结果；只有显式 `--quiet` 可以 rc=0 且无输出。

这样以后“rc=0”终于真正等于“做了预期的事情”。

---

### 2. 把“测试结束后清 data”改成“测试根本写不到 repo”

现在 `conftest.py` 的污染检测应该保留，但降级为**最后一道保险**。

真正的解决办法是引入运行环境对象：

```python
@dataclass(frozen=True)
class RuntimePaths:
    root: Path
    snapshots: Path
    guide_db: Path
    published_db: Path
    assets: Path
    raw: Path
    cache: Path
    staging: Path
    reports: Path
```

解析优先级建议：

```text
CLI --data-dir
    ↓
HSRMAP_DATA_DIR
    ↓
OS user-data directory
```

测试则永远注入 `tmp_path`。

`hsrmap.paths` 当前这种：

```python
ROOT = ...
DATA = ROOT / "data"
```

最终应该只用于**源码/资源定位**，不能再决定 mutable state 写在哪里。

---

### 3. 数据库必须区分 read / write / create

这是一个非常值得优先改的地方。

目前：

```python
GuideDatabase(path)
```

隐含了：

```text
mkdir
+
create sqlite
+
CREATE TABLE
+
migration
```

这意味着“我只是想看一下有没有数据库”都有机会改变文件系统。

目标 API 应该显式：

```python
GuideDatabase.open_readonly(path)
GuideDatabase.open_readwrite(path)
GuideDatabase.create(path)
```

或者：

```python
GuideDatabase(path, mode=DbMode.READ_ONLY)
```

其中：

```text
viewer/published lookup   → READ_ONLY
audit of existing DB      → READ_ONLY
admin/workflow mutation   → READ_WRITE
new working DB            → CREATE
```

只允许 `CREATE` 路径执行 mkdir/schema bootstrap。

这样 `tests/conftest.py` 里那段“测试居然建出了 data/”会从常态防御变成真正的异常检测。

# 五、Evidence 一等化：不要只给 `guide_entry` 加一个字符串

这是整个计划里最重要的模型设计。

你之前提的：

```text
official
community-text
transcription
cross-inference
```

方向完全对，但我**不建议只做**：

```sql
ALTER TABLE guide_entry ADD COLUMN evidence_level TEXT;
```

因为实际情况是：

> 一个攻略可能“LOCATE 来自官方地图，SOLVE 来自社区正文”；甚至一条攻略里有几步正文、一两步图解转录。

所以 evidence level 应该属于**claim**，而不是整篇攻略。

建议新增：

```text
guide_claim_evidence
─────────────────────────────────
id
guide_id
step_id                 nullable
target_id               nullable

claim_kind
  SCOPE
  LOCATE
  SOLVE

evidence_level
  OFFICIAL
  COMMUNITY_TEXT
  TRANSCRIPTION
  CROSS_INFERENCE

grounding_tier
  EXACT
  FRAGMENT
  ASSEMBLED
  IMAGE_REF
  DERIVED

source_page_id           nullable
official_point_id        nullable
asset_sha256             nullable

basis_json               nullable
method_version
created_at
```

这样当前 `audit.py` 的成果完全不用扔掉：

```text
EXACT
FRAGMENT
ASSEMBLED
NONE
```

它们成为 `COMMUNITY_TEXT` 下的 grounding 子类型。

现有：

```text
[图解法转录 <sha>]
```

迁移成：

```text
evidence_level = TRANSCRIPTION
asset_sha256 = ...
grounding_tier = IMAGE_REF
```

而交叉推断必须留下：

```text
evidence_level = CROSS_INFERENCE
basis_json = [参与推断的 evidence IDs / source refs]
```

不能只留下一个“人判断过了”。

## 完成度也不要再只输出一个 1006/1006

现有六状态继续保留，**完全不修改语义**。

新增的是“这个完成状态靠什么证据成立”。

每个点位输出：

```json
{
  "status": "COMPLETE",
  "locate_evidence": "OFFICIAL",
  "solve_evidence": "TRANSCRIPTION"
}
```

然后整体统计拆成：

```text
Direct complete
    只需要 OFFICIAL / COMMUNITY_TEXT 即成立

Transcription-assisted complete
    需要加入 TRANSCRIPTION 后才能成立

Inference-assisted complete
    必须加入 CROSS_INFERENCE 才成立

Incomplete
```

这样未来即使还是：

```text
all completion = 1006 / 1006
```

用户同时看到：

```text
direct       = ...
transcribed  = ...
inferred     = ...
missing      = ...
```

这里尤其不要人为写死“最后 3 个就是 3 个 inferred”。让 backfill 自己重新算。

# 七、把 `%TEMP%\rNN*.py` 的能力回收到三个正式 workflow

```text

```

所有重复执行必须 idempotent，至少不能重复制造逻辑相同的账本。

# 十二、性能：先消灭查询结构问题，再做微优化

这里不建议缓存补丁式优化。

当前至少有两个 N+1。

`completeness_report()`：

```text
1006 points
  └── _best_entry()
       └── matching entries query
            └── each entry
                 ├── steps query
                 └── assets query
```

`GuideDatabase.list_for_keys()`：

```text
entries query
  └── each entry _entry()
       ├── steps query
       └── assets query
```

目标应该改成一次预加载：

```text
SELECT published entries
SELECT all steps WHERE guide_id IN (...)
SELECT all assets WHERE guide_id IN (...)
SELECT entry targets
```

然后建立：

```python
entries_by_point
steps_by_guide
assets_by_guide
targets_by_guide
```

整个 1006 点位循环不再碰 DB。

更进一步，`stages.py` 已经存在 `guide_entry_target` 正规关系表，就应该逐渐替换：

```text
source_point_id LIKE '%123%'
set:...
正则抽数字
```

迁移策略是：

```text
现有字符串 lookup
+
target relation lookup
→ shadow compare
```

只有输出完全一致后再切过去。

这既解决性能，也解决你之前提到的“路径特判”。

另外增加这些 index：

```text
guide_entry(status, source_point_id)
guide_steps(guide_id, step_index)
guide_assets(guide_id, step_index)
guide_entry_target(target_id, guide_id)
```

性能验收我不建议先拍脑袋定“必须 2 秒”。

先固定两个更可靠的指标：

```text
SQL query count 不再与 point count 成正比
closure 中同一个 snapshot/completeness 不重复完整计算
```

再在当前硬件上录 wall-clock baseline，作为后续回归预算。

# 十五、其中最关键的迁移保护：shadow mode

这一项目现在最大的资产是**判定结果可信**，所以卫生化绝不能以“顺手重写”为名改变结果。

S1～S7 都应该遵守：

```text
old implementation
        │
        ├── result A
        │
new implementation
        └── result B

assert normalize(A) == normalize(B)
```

例如新的 target relation 取代 `set:` 字符串时：

```text
旧 _best_entry(point)
新 PublishedGuideIndex.best_entry(point)

1006 个逐点 compare
```

Evidence 模型上线时：

```text
旧 point_status
新 evidence provenance → point_status

六状态必须完全一致
```

只有“新增的证据等级字段”允许出现变化。

这会让整个卫生化过程变成**可证明没有动业务语义的重构**。

---

# 十六、最终 Definition of Done

我会把这轮“卫生化完成”定义成下面 12 项全部成立：

1. `python -m hsrmap.cli` 不再静默成功。
2. clean checkout 执行普通测试不会创建 `data/`。
3. viewer/read-only 操作不会隐式创建 SQLite。
4. repo 中没有 runtime DB、cache、submit、bak、nested zip、generated web dist。
5. `phase1` 只留下真正需要版本管理的 reference/fixture。
6. 发布包由 allowlist/build pipeline 生成，不通过手工镜像目录。
7. 所有数据库有明确 schema version。
8. `%TEMP%\rNN*.py` 不再承担任何当前生产流程。
9. 每个完成点位都能给出 LOCATE/SOLVE 的 evidence provenance。
10. 1006/1006 不再能掩盖 transcription / inference。
11. completeness/closure 不存在逐点 N+1。
12. Web 能直接回答：**“这条为什么算完成，它依据的是什么？”**

---

我认为这套方案里最值得坚持的一点是：**这不是“清理仓库”，而是把项目已有的证据纪律贯彻到工程本身。**

现在数据结论已经有 provenance、检索有 ledger、发布有 gate；下一步只是让**命令、数据库、运行目录、发布物、迁移和性能也具备同样的可追踪性**。完成以后，这个项目的工程形态会和它的判定层处在同一个成熟度级别，而不是继续靠作者个人记忆维持。
