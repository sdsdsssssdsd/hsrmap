对，这个逻辑应该放在**攻略完整性判定层**，而不是简单用“有没有第三方攻略/有没有详细步骤”判断。你说的关键点我会按下面的模型理解：

> **官方图片不是低级证据。只要它足以让玩家准确到达目标位置，而且目标到点即可取得，那么它本身就是完整攻略。**
> 只有“到点之后还必须继续操作”时，才需要第二阶段攻略。

而且最新版代码里其实已经开始出现这个方向：`guide-completeness.md` 已定义 `LOCATE / INTERACT / PUZZLE`，但我建议进一步简化并提升成你说的**两阶段模型**，这样业务含义更准确。

## 一、核心逻辑层：不是“攻略详细不详细”，而是“玩家能不能拿到”

### 第一阶段：定位到点 `STAGE_1_LOCATE`

问题只有一个：

> **用户根据现有证据走到这个地图点以后，是否已经可以直接取得目标？**

如果答案是“是”，那么攻略已经 **100% 完整**。

证据可以只是：

* 官方地图点；
* 官方点位截图；
* 官方“一行位置说明”；
* 第三方位置截图；
* 足以唯一定位的地图图片。

甚至一张官方图片，只要能完成导航，就是最完善的攻略，不应该因为“没有文字步骤”被降级。

因此：

```text
官方图片
    ↓
能唯一定位到目标
    ↓
到点直接获得
    ↓
COMPLETE
```

这里不需要第二阶段。

---

## 二、第二阶段：到点后的完成方法 `STAGE_2_SOLVE`

第二个问题：

> **玩家已经站在正确位置了，但东西仍然拿不到吗？**

如果是，那么位置证据只完成了 Stage 1。

还必须回答：

> 到这里以后具体怎么做？

例如：

```text
到达机关
↓
进入解谜
↓
旋转 / 移动 / 输入方向 / 对话 / 变身 / 跳跃
↓
完成
↓
取得奖励
```

这才需要真正意义上的“解法攻略”。

所以完整性应该是：

```text
需要 Stage 1 的目标：
LOCATE ✓ = COMPLETE

需要 Stage 2 的目标：
LOCATE ✓ + SOLVE ✓ = COMPLETE
LOCATE ✓ + SOLVE ✗ = LOCATION_ONLY / INCOMPLETE
```

---

# 三、按这个逻辑重新分类当前需要攻略的 Topic

我建议不要再把 `COLLECTIBLE / PUZZLE / CHALLENGE` 当成“攻略完整性”的主分类。

它们可以继续作为**内容类型**存在。

攻略需求另外增加：

```text
completion_requirement:
    LOCATE_ONLY
    LOCATE_AND_SOLVE
```

这是两个正交维度。

---

## A 类：第一阶段就能完成——找到位置 = 攻略完成

### 1. 折纸小鸟 `origami_bird`

**分类：LOCATE_ONLY**

玩家真正缺的是：

> 鸟在哪里？

如果官方点位图片已经能准确告诉用户位置，用户走过去即可收集，那么：

```text
官方位置图 = 完整攻略
```

不应该要求额外第三方“操作攻略”。

所以 MAP_LABEL 形式的“该地图共 N 只”只能证明**范围/数量**，不能单独完成 Stage 1；但如果同时存在每个点的官方截图/官方点位，那么就够了。


不需要为了追求“攻略文章”再找额外文字。

### 3. 无名尘灵 `nameless_dust_spirit`

原则上：

**分类：LOCATE_ONLY**

真正需要解决的是：

> 尘灵到底藏在哪里？

如果官方截图足以定位：

```text
官方图 ✓
→ Stage 1 ✓
→ COMPLETE
```

这也解释了为什么以前把“纯文字攻略不足”看得太重。

对这种 Topic：

不是图片附属于文字攻略。

### 4. 次元扑满 `dimensional_trotter`

我建议归：

**LOCATE_ONLY 为主。**

攻略核心是扑满位置。

玩家到目标区域发现扑满后，正常游戏行为即可解决；通常没有一个独立的谜题状态机需要攻略去解释。

```text
定位准确
→ 攻略基本完成
```

这意味着阶段最好允许：

```text
Topic default + Point override
```

# 四、B 类：必须第二阶段——到达位置还不够

这里才是真正需要继续找“解法攻略”的对象。

### 1. 浮脂溯源·二次元 ROTATE `floating_grease`

**典型 `LOCATE_AND_SOLVE`。**

这正是你说的典型案例。

官方图片可能已经完美解决：

> 浮脂溯源在哪里？

但是玩家走到那里以后：

```text
找到机关
≠
拿到奖励
```

还需要：

```text
进入机关
→ 操作 ROTATE
→ 正确旋转/输入
→ 完成解谜
```

因此它应该拆成：

```text
Stage 1
位置证据
✓

Stage 2
具体 ROTATE 解法
？
```

这也意味着当前所谓：

> 浮脂 34 个“只有位置”

不是“34 个攻略很差”。

更准确应该叫：

> **34 个 Stage 1 已完成、Stage 2 待补。**

这是非常重要的语义变化。

### 2. 黄金替罪羊 `golden_scapegoat`

**LOCATE_AND_SOLVE**

找到替罪羊机关只是 Stage 1。

之后还要完成输入/行动序列。

所以完整攻略：

```text
位置
+
上下左右等完整输入序列
```

Stage 2 对这个 Topic 特别容易机器判断，因为它属于：

```text
INPUT_SEQUENCE
```

因此可以建立 deterministic validator：

```text
有 target location
+
有合法方向序列
=
COMPLETE
```

### 3. 梦境迷钟 `dream_ticker`

**LOCATE_AND_SOLVE**

位置图只能解决：

> 迷钟在哪。

到达以后仍然需要操作模块完成谜题。

所以：

```text
Stage 1 = 找到迷钟
Stage 2 = 模块移动/旋转解法
```

它属于：

```text

```

完整性要求明显高于单纯位置。

### 4. 小小哈努行动 `hanu`

位置只是入口。

之后涉及：

```text

→ 变身
→ 移动
→ 机关/路线
```

因此官方入口图片并不能证明完整攻略。

不过它和迷钟不同：

所以第二阶段证据最好是：

# 六、“该地图共 N 个”应该单独建第三种证据概念

你特别指出的这一点也非常重要。

比如：

> 「这个地图共有 4 个浮脂溯源」

它不是错误证据。

但它证明的是：

```text
SCOPE
```

而不是：

```text
LOCATE
```

所以证据最好明确拆成：

```text
SCOPE
LOCATE
SOLVE
```

这三个不是三个完成阶段，而是三种 evidence capability。

例如：

### “该地图共 4 个”

```text
SCOPE ✓
LOCATE ✗
SOLVE ✗
```

### 官方地图给出四个准确点位

```text
SCOPE ✓
LOCATE ✓
SOLVE ✗
```

### 浮脂攻略给出四个点 + 每个 ROTATE 解法

```text
SCOPE ✓
LOCATE ✓
SOLVE ✓
```

对于若虫：

```text
SCOPE ✓
LOCATE ✓
SOLVE N/A

→ COMPLETE
```

对于浮脂：

```text
SCOPE ✓
LOCATE ✓
SOLVE ✗

→ STAGE_1_COMPLETE
```

这就完全解决你说的“官方图片其实可能就是正确的、最完善的攻略”的问题。

# 七、建议最终数据模型

我会把现有：

```text
LOCATE
INTERACT
PUZZLE
```

改造成两个维度，而不是三个平级阶段。

### 维度一：完成需要走到哪一步

```text
completion_requirement:

LOCATE_ONLY
LOCATE_AND_SOLVE
```

### 维度二：Stage 2 是什么

```text
solve_kind:

NONE
INTERACT
INPUT_SEQUENCE
MODULE_PUZZLE
TRANSFORM_ROUTE
PLATFORM_ROUTE
CHALLENGE
OTHER
```

然后证据：

```text
evidence:

scope:
    status

locate:
    status
    evidence_ids

solve:
    status
    evidence_ids
```

最后计算：

```python
if requirement == LOCATE_ONLY:
    complete = locate.complete

elif requirement == LOCATE_AND_SOLVE:
    complete = locate.complete and solve.complete
```

非常干净。

# 八、这样会直接改变 Corpus 搜索策略

这是最大的实际收益。

以后不能再问：

> 这个 Topic 有没有攻略？

而要问：

> **这个 target 缺的是 LOCATE，还是 SOLVE？**

### 折纸小鸟缺 LOCATE

搜索：

```text
折纸小鸟 + 地图名 + 位置
```

图片价值最高。

找到可靠官方截图以后：

**停止搜索。**

不用再找所谓“详细攻略”。

### 浮脂已经有 LOCATE

就绝对不要继续搜：

```text
浮脂在哪里
```

而应该只搜：

```text
浮脂 + 地图名 + 解法
浮脂 + 地图名 + ROTATE
浮脂 + 点位名 + 操作
```

因为 Stage 1 已经完成。

### JUMP 已知入口

直接搜索：

```text
JUMP + 地图 + 路线
JUMP + 地图 + 通关
```

而不是继续积累入口截图。

这样 crawler 的 target-driven discovery 才真正聪明。

# 九、最终应该把“攻略完整度”表达成状态，而不是百分比

我不建议搞：

```text
攻略完整度 75%
```

这种分数没有稳定语义。

用状态：

```text
NO_EVIDENCE
SCOPE_ONLY
LOCATE_MISSING
LOCATE_COMPLETE
SOLVE_MISSING
COMPLETE
```

更准确。

例如当前浮脂某点：

```text
Requirement: LOCATE_AND_SOLVE

SCOPE     PASS
LOCATE    PASS
SOLVE     MISSING

Result:
STAGE_1_COMPLETE
```

而若虫某点：

```text
Requirement: LOCATE_ONLY

LOCATE    PASS
SOLVE     N/A

Result:
COMPLETE
```

两者可能拥有**完全相同质量的官方点位图片**，但最终状态不同——不是因为图片质量不同，而是因为游戏机制不同。

这正是你要求建立的那层“逻辑”。

## 对当前项目最关键的重新定义

以后应该彻底放弃：

> **“文字攻略比官方图片更完整。”**

正确规则应该是：

> **攻略是否完整，只由玩家从当前证据出发能否最终取得目标决定。**

所以：

**收藏物：**

```text
准确官方位置图
→ 用户到点
→ 获得
→ COMPLETE
```

**浮脂溯源：**

```text
准确官方位置图
→ 用户到点
→ 还没获得
→ STAGE 1 COMPLETE
→ 缺 SOLVE
```

**黄金替罪羊：**

```text
位置
→ 到达
→ 仍需输入序列
→ 缺序列则不完整
```

**JUMP：**

```text
入口
→ 到达
→ 仍需完成路线挑战
→ 缺路线则不完整
```

这个逻辑层一旦进入 Ledger，后面的**爬虫检索词、Review admission、Coverage、攻略完整性、下一步任务生成**都应该围绕 `missing LOCATE / missing SOLVE` 自动推导，而不是继续围绕笼统的 `NEEDS_SOURCE` 运转。
