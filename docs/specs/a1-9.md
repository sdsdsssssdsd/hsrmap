# 3. 最大的风险其实不是 API，而是“状态语义”

现在实际上存在至少三种完全不同的 `completed`：

```text
A. 游戏世界真实状态
   玩家在游戏里已经开过这个宝箱

B. 官方互动地图账号状态
   玩家在官方地图上把这个点标记为已获取

C. Hoyo / Guide Atlas 本地状态
   玩家在你的程序里勾选 completed
```

目前 `user.db.completed` 表达的是 C。

而新接口首先能比较有把握得到的是 B。

至于：

```text
B == A ?
```

现在没有充分证据。

而且你提供的逆向证据中：

```text
save_point_status(point_id, mark_status)
```

会改变状态，并且 UI 计数即时变化。

这实际上是一个非常强的信号：

**至少 `point_status` 包含“互动地图自己的用户标记状态”。**

因此我不会采用原方案中的这一句：

> 官方点状态直接写 `completed=1`

因为一旦后来证明 B ≠ A，你就无法区分：

```text
玩家自己在 Guide Atlas 勾的
官方地图导入的
游戏真实同步来的
```

这会形成数据污染。

# 7. 不要假设 `ltoken_v2 + ltuid_v2` 永远够用

这一点原分析稍微乐观了一些。

现有第三方实现/问题记录可以证明 `getUserGameRolesByCookie` 确实是被实际客户端使用的角色查询接口；海外实现使用的是 `api-os-takumi...` 一族，而不是把国服 binding host 原样复用。([GitHub][2])

同时历史上 V2 Cookie 组合本身就出现过兼容性变化。([GitHub][3])

所以代码不要写成：

```python
required = ["ltoken_v2", "ltuid_v2"]
```

应该把 Cookie 当 opaque credential：

```python
cookie: str
```

程序只负责：

```text
存在？
→ 发请求
→ 判断 retcode
→ 给出诊断
```

不要负责猜用户缺哪个 Cookie。

这样官方以后再变：

```text
ltmid
cookie_token
account_mid
...
```

你的程序不用跟着改认证模型。

# 17. 推荐的正式 Roadmap

我建议下一阶段定为：

## Phase 6 — Personal Progress Layer

只做账号状态读取和语义隔离。

唯一硬目标：

> **在完全不影响现有 credentials-free pipeline 的情况下，安全获得并解释官方账号地图状态。**

可以拆成这一条实施链：

1. **P6.0 Contract Discovery**：重新解析当前 bundle，扩充 endpoint registry，记录 method/auth/mutating/request/response fingerprint；发现失败必须 fail closed。
2. **P6.1 Auth Boundary**：独立 `progress` package、opaque Cookie provider、日志脱敏、禁止写接口、CN/global realm registry。
3. **P6.2 Semantic Probe**：实现 role → treasure count → point status，但只输出诊断报告，不写 `user.db`；完成上面的 2×2 实验。
4. **P6.3 Observation Store**：增加 `progress_profile` / `progress_observation`，保留 manual/map/game 三种来源，不改变现有 `completed` 语义。
5. **P6.4 Progress Diff**：产出 `local_only / remote_only / both / unknown`，默认 dry-run；用户明确确认才允许 merge。
6. **P6.5 Remaining Atlas**：`remaining = collectible − effective_completed`，直接 join 现有 Guide Atlas 的坐标、LOCATE/SOLVE、攻略图和步骤。
7. **P6.6 Viewer Integration**：地图增加 `All / Remaining / Completed / Conflict` 过滤器和“官方地图同步”状态，但 Viewer 本身继续不直接发外网。
8. **P6.7 Route Planner**：最后才做区域聚类、路径排序、连续清图路线。

```text
          ↓
    Route Planner
```

这会多花一点前置工作，但会避免整个项目最难修复的一类 bug：

**“同步成功了，但同步的是错误语义的数据。”**

---

## 最终判断

所以，对于你贴出来的调查结果，我给的评价是：

**接口发现与现有项目架构判断基本成立，足以立项；但“官方进度 = 游戏真实收集进度”目前仍然没有证实，而且这是唯一不能跳过的关键验证。**

另外我会明确否掉一个实现选择：**现在不要只写一个 `tools/srmap_user_export.py` 然后直接更新 `point_progress.completed`。** 你的项目已经不是一次性脚本的规模了；README 里现有 1006 点、Guide Atlas、evidence/audit/publishing/user-state 这些体系已经足够成熟，新能力应该作为正式的 `progress` domain 进入架构。

最优下一步应当是 **P6.0 + P6.1 + P6.2**：先做“动态 endpoint contract + 只读认证客户端 + semantic probe”，跑完那组 2×2 实验。只要实验结果出来，就能无歧义决定后面的数据库模型究竟走 `map_mark`，还是直接升级成真正的 `game_obtained`。

这一步确认之后，项目最值得投入的方向就不再是继续扩大攻略 corpus，而是 **Remaining Atlas → Next Action → Route Planner**；那会把现有 Guide Atlas 从“攻略证据引擎”真正变成个人清图工具。
