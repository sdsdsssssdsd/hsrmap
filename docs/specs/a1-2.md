**可行，而且我建议做。** 但不要把它理解成“把现在的离线 Viewer 改成 WebSocket 连 HoYo”。更合适的是新增一层 **Live Provider / Hybrid Mode**：浏览器仍然只连 `127.0.0.1`，本地 FastAPI 作为网关去请求 HoYo 当前公开地图接口。这样你现在已经做好的 CSP、离线快照、`core.db/detail.db`、原子更新机制全部不用推倒。

截至现在官方 HSR 互动地图入口仍正常提供网页服务。([HoYoverse][1]) 结合你已经实测通过的匿名 `map/tree → map/info → point/list → point/info` 链路，**本地后端实时读取官方公开数据在技术上没有结构性障碍**。

## 我建议最终做成三种数据模式

| 模式         | 数据来源                      | 用途       |
| ---------- | ------------------------- | -------- |
| **离线**     | `core.db + detail.db`     | 完全断网、最稳定 |
| **混合在线** ⭐ | HoYo 在线优先，失败回退本地 Snapshot | 日常默认     |
| **强制在线**   | HoYo 当前公开 API             | 调试、核对新版  |

我最推荐 **混合在线**。

架构从现在的：

```text
Browser
   ↓
FastAPI
   ↓
core.db / detail.db / assets
```

变成：

```text
                         ┌─ SnapshotProvider
                         │   core.db
Browser                  │   detail.db
   │                     │   assets
   │ localhost           │
   ▼                     │
FastAPI ─→ HybridProvider┤
                         │
                         └─ LiveProvider
                              │
                              ▼
                       HoYoLAB HSR Public API
```

浏览器**仍然不直接访问 HoYo**。

这点非常重要。

# 为什么不建议浏览器直接连 HoYo

理论上可以先做一个小实验，但我不会把正式架构建在它上面。

浏览器直连要同时满足：

```text
HoYo API
  ↓
允许 Origin: http://127.0.0.1:8765
  ↓
CORS 成功
```

你之前发现官方前端使用：

```text
withCredentials=false
```

只能证明“不需要 Cookie”，**不能证明它允许 localhost 跨域**。

而本地 FastAPI 后端请求不存在浏览器 CORS 限制。

所以最稳的是：

```text
Browser
   ↓ same-origin
127.0.0.1
   ↓ server-side HTTP
HoYo
```

现有 CSP 甚至可以继续保持：

```text
connect-src 'self'
```

不用为了 Live Mode 放开：

```text
*.hoyolab.com
*.hoyoverse.com
```

安全性反而更好。

# “实时”具体怎么定义

这里要稍微修正一下概念。

HoYo 当前这些地图接口是：

```text
GET map/tree
GET map/info
GET label/tree
GET point/list
GET point/info
```

它们特别适合：

> **按需获取当前官方数据**

但这不意味着需要建立一个永不断开的长连接。

对于互动地图来说，真正有价值的 Live Mode 是：

```text
用户打开地图
        ↓
请求当前官方 map/info
        ↓
请求当前官方 point/list
        ↓
显示当前官方版本

用户点击 marker
        ↓
请求当前 point/info
```

这已经是真正意义上的“在线看官方当前数据”。

如果用户把一个页面开着几小时，可以再：

```text
每 5～10 分钟
检查当前 map 的 point/list hash
```

有变化：

```text
官方地图数据有更新
[立即刷新]
```

完全没必要：

```text
每秒轮询
```

更没必要自己造 WebSocket。

# 最关键的架构：DataProvider

现在就应该把 Viewer 的数据源抽象掉。

例如：

```python
class MapDataProvider:
    async def get_tree(self): ...
    async def get_labels(self): ...
    async def get_map(self, map_id): ...
    async def get_points(self, map_id): ...
    async def get_point(self, point_id): ...
```

然后：

```text
SnapshotProvider
LiveProvider
HybridProvider
```

### SnapshotProvider

就是目前已经有的：

```text
core.db
detail.db
assets
```

### LiveProvider

调用当前官方 HSR API。

### HybridProvider

核心逻辑：

```text
Live 成功
    ↓
返回 Live

Live 暂时失败
    ↓
Live Cache

Cache 也没有
    ↓
Snapshot
```

这样前端根本不用分别写两套页面。

例如现在前端还是调用：

```text
GET /api/v1/maps/508/points
GET /api/v1/points/5171
```

不要变成：

```text
/api/live/...
```

返回增加：

```json
  },

  "data": {}
}
```

来源可以是：

```text
live
live-cache
snapshot
```

这对调试特别有用。

# Live Cache 不要污染 Snapshot

非常重要。

在线读到的新数据：

**绝对不要直接写进：**

```text
core.db
detail.db
```

建立：

```text
data/live-cache/
```

例如：

```text
data/
├─ snapshots/
├─ enrichments/
├─ assets/
├─ live-cache/
└─ user/
```

Live Cache 只是：

```text
HTTP cache
```

可以随时：

```text
rm -rf live-cache
```

不会影响：

```text
Offline Snapshot
User Progress
Guide
```

# Live Asset 怎么处理

这里也不要让浏览器直接加载：

```text
https://....hoyolab....
```

例如远程 `map/info` 返回新的 Raster。

FastAPI：

```text
HoYo image
   ↓
stream/download
   ↓
local live-cache
   ↓
/api/v1/live-assets/<key>
   ↓
Browser
```

Detail 图片同理。

如果内容下载完成，可以：

```text
SHA256
```

做缓存去重。

但仍然标记：

```text
cache
```

而不是正式 Snapshot Asset。

# 在线与离线版本不一致时，绝对不要字段级混合

这是一个很容易出现的大坑。

例如：

```text
Snapshot map/info
+
Live point/list
```

有可能碰上官方刚改地图：

```text
origin 变了
raster 变了
points 也变了
```

然后 marker 全错。

所以必须以**逻辑对象批次**处理。

加载一张在线地图时：

```text
map/info
+
point/list
```

必须来自同一个 Live Session / Remote State。

不能：

```text
map_info = local
point_list = live
```

除非明确验证兼容。

最简单：

```text
Live map usable?
    Yes → map + points 都 Live
    No  → map + points 都 Snapshot
```

Detail 可以独立，因为 point identity 已经确定。

# 连接建立时做一次轻量 Discovery

Live Provider 不应该继续永久写死：

```text
sg-act-public-api-static...
de16a09...
```

连接流程：

```text
Connect Live
    ↓
GET 官方 HSR interactive-map index
    ↓
发现当前 bundle
    ↓
bundle SHA
    ↓
public API host
    ↓
app_version
    ↓
probe map/tree
    ↓
required schema
    ↓
ONLINE
```

如果：

```text
bundle SHA changed
```

但 required Schema 兼容：

```text
继续在线
```

如果：

```text
Required Schema changed
```

则：

```text
LIVE_INCOMPATIBLE
```

自动回退 Offline。

同时提示：

```text
官方地图接口已变化；
离线地图仍可正常使用。
```

这个设计会非常稳。

# 建议的缓存 TTL

不需要所有接口一样。

| 数据                   | 推荐行为                      |
| -------------------- | ------------------------- |
| bundle / API version | 启动检查 + 30min              |
| `map/tree`           | 30min                     |
| `label/tree`         | 30min                     |
| `map/info`           | 打开地图时获取；5–10min cache     |
| `point/list`         | 打开地图时获取；5–10min cache     |
| `point/info`         | 点击时获取；30min/session cache |
| Raster/icon/image    | 内容缓存，不定时重复下载              |

如果用户点：

```text
刷新当前地图
```

忽略 TTL，强制重新 GET。

# 开发顺序

我会把这项插在 Viewer 路线中，作为 **Phase 4L — Live Data Layer**。

| Sprint | 内容                    | 验收                               |
| ------ | --------------------- | -------------------------------- |
| **L0** | CORS/endpoint 小 Spike | 确认直连是否可能，但不依赖它                   |
| **L1** | `DataProvider` 抽象     | 现有离线 Viewer 无回归                  |
| **L2** | `LiveProvider`        | map/tree/info/points/detail 在线成功 |
| **L3** | `HybridProvider`      | 断网自动回退                           |
| **L4** | Live Asset Cache      | Raster/detail 图可在线看              |
| **L5** | Provenance UI         | Online/Cache/Snapshot 可见         |
| **L6** | Active map refresh    | 变化检测                             |
| **L7** | Snapshot bridge       | 在线发现新版→启动完整离线更新                  |

# 必须做的故障测试

Live 系统最重要的测试不是“网络正常”。

而是：

1. HoYo 正常 → 当前官方数据。
2. DNS 失败 → Snapshot 正常。
3. HoYo 500 → Snapshot 正常。
4. API timeout → Snapshot 正常。
5. Schema 改变 → 禁用 Live，不破坏 Viewer。
6. Raster 在线失败 → 整张地图回退 Snapshot，而不是半 Live。
7. 用户正在看 Point 时断网 → 当前内容继续可读。
8. 网络恢复 → 下一次刷新重新 Live。

做到这些，Live Mode 才有意义。

---

# 有一个现实问题：这不是官方开放 API

技术上可行和“官方授权使用”是两回事。

我目前看到的 HoYoverse 最新服务条款仍明确限制未经许可的复制、下载、抓取、再分发等行为；因此这些前端接口应该继续视为**未文档化的内部公开网页接口**，而不是一个有稳定 SLA 的官方开发者 API。([Genshin Impact][2])

所以如果只是你个人本地研究，技术方案可以保持低并发、只读、匿名、缓存和 Snapshot fallback；但不要据此认为 HoYo 承诺这些接口长期稳定，也不建议把抓下来的官方资产整包公开分发。

---

## 最终判断

**能建立，而且值得建立。**

但最优方案不是：

```text
浏览器 ↔ HoYo
```

也不是：

```text
WebSocket ↔ HoYo
```

而是：

```text
                  ┌→ HoYo 当前公开地图数据
Browser → FastAPI ┤
                  └→ 本地完整 Snapshot
```

做成一个 **Live + Offline 双引擎 Viewer**。

这样你会得到一个很强的组合：

```text
有网：
看到 HoYo 当前地图

断网：
瞬间回退完整 624 地图

官方刚更新：
Live 立刻可以看

需要永久保存：
跑 Snapshot Pipeline

官方 API 改坏：
老 Snapshot 照常工作
```

这比把现有纯离线架构直接改造成纯在线客户端要稳得多。
