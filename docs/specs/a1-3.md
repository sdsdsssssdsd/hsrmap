对，这一步就应该正式进入 **Phase 5：Guide Overlay / 攻略采集系统** 了。

而且不应该理解成“写个爬虫把网页扒下来塞进详情框”。更稳的设计是：

> **网页发现 → 抓取原文/图片 → 内容块解析 → DeepSeek 结构化 → 精确匹配到本地 point_id → 人工审核低置信结果 → 发布到独立 guide.db → Viewer 完全离线显示。**

你现在这个项目已经有一个很好的雏形：上传的代码里已经存在 `guide_db.py`、`guide_entry / guide_steps / guide_assets`，也已经有 `/api/v1/guides/by-point/{source_point_id}`。所以不是从零开发，而是把这个“手工 Guide DB”升级成一套完整的**攻略采集生产线**。

目前网上的图文资源也足够支撑这么做：TapTap 有 4.1、4.3 的专门浮脂图文帖；17173 有 4.2 海原市/电视塔 6 个解谜的图片攻略；游民星空有 4.0 汇总；3DM 的 4.2、4.3 页面又明确标注来源为米游社、作者祈鸢ya。也就是说，同一套攻略经常存在“原作者页 + 多个转载页”，所以**去重和找原始来源**必须从第一天就设计进去。([TapTap](https://www.taptap.cn/moment/786205107434815910?utm_source=chatgpt.com))

                       │
                       ▼

              original images
                       │

                       │

## 这套里面 DeepSeek 最适合干什么

一句话：

**不要让 DeepSeek 找攻略；让它读攻略。**

爬虫决定：

> “这一页是什么。”

本地 DB 决定：

> “有哪些真实 Point。”

OpenCV 决定：

> “攻略地图截图到底落在官方 Raster 的哪里。”

DeepSeek 决定：

> “这一段在讲哪个地图、分几步、这些图片分别是什么意思、文字步骤如何结构化。”

这几个各干各最擅长的事，可靠性会高很多。

并且 DeepSeek 当前接口本身支持严格 JSON 输出，也有图像输入能力，所以特别适合做这一层的结构化抽取，而不是靠正则硬解析所有作者不同的写法。([DeepSeek API Documentation](https://api-docs.deepseek.com/guides/json_mode/?utm_source=chatgpt.com))
