# 5. 第一层：Endpoint Discovery

这是整个项目最重要的一层。

绝对不要写：

```python

```

然后假定永远有效。

## Discover 工作流程

启动：

```bash
python -m hsrmap discover
```

程序：

```text
启动 Playwright Chromium
        ↓
新建无痕 Context
        ↓
不载入任何用户 Cookie
        ↓
打开 HSR 官方互动地图
        ↓
监听 request / response
        ↓
识别 HSR Map JSON
        ↓
记录 API
        ↓
识别版本信息
        ↓
生成 endpoint_registry.json
```

需要监听：

```text
request.url
request.method
request.headers
response.status
response.headers
response.content-type
JSON body
```

以下请求头不得持久化：

```text
Cookie
Authorization
Set-Cookie
x-rpc-device_id
x-rpc-device_fp
```

默认不要保存 HAR。

只有：

```bash
--debug-har
```

才允许输出 HAR，并且明确提示可能含敏感请求信息。

# 8. Schema Fingerprinting

每个发现到的 JSON API 自动生成结构指纹。

例如：

```text
data.info.id
data.info.name
data.info.detail
data.info.detail.total_size
data.info.detail.slices[][]
```

计算：

```text
SHA256(sorted JSON paths)
```

保存：

```text
schema_fingerprint
```

这样 HoYoLAB 改接口以后可以检测：

```text
endpoint URL 没变
但是 Schema 变了
```

并停止危险的错误更新。

这是整个项目最正确的下一步。

其中我最建议你让本地开发**严格卡住一个里程碑**：先别做 UI，先证明“当前 2026 年的 HSR 官方地图 → 一张底图 → 20 个真实点位 → 坐标完全对齐”。这一步过了，后面 80% 都是普通工程问题；这一步没过，先做再漂亮的界面都没意义。

旧 HSR 实现已经证明过地图 `detail → total_size/slices → 切片合成` 这条技术路线是存在的，同时也证明 `app_version` 曾经是从 HSR 官方前端 bundle 动态取得，而不是固定常量。([Gist](https://gist.github.com/c2t-r/5393923a78a09e3e510165200eac74a2)) 因此这份方案特意把**接口发现和版本检测放在第一层**，会比“照旧脚本重写一个爬虫”稳很多。

这份 Spike 我认可，已经足够从“可行性研究”转入正式 Phase 1。**现在不要做全量下载器，也不要做正式 UI；先把协议冻结 + 坐标系统证明出来。**

不过正式开工前，我会纠正/收紧 4 个点：

1. **923 个 `map/tree` 节点 ≠ 923 张需要下载的地图。** 树里很可能同时有星球、区域、分组、楼层、实际可渲染地图。必须先分类，只有真正拥有可用 `map/info.detail` 的节点进入 raster 同步队列。
2. **`app_version` 不要当“前端版本”。** 它两年没变，说明它更像 API 客户端版本/协议参数。真正用于判断前端是否变化的应该是 `bundle URL + bundle SHA256 + endpoint host + schema fingerprint`。
3. **`total_size=[8192,4096]` 但只有 1 个 slice 非常重要。** 彻底放弃“固定 2048 网格”的抽象。Normalizer 应该把官方 `slices` 转成“任意矩形 raster fragment”，单张整图、多切片都走同一种数据模型。
4. **`point_info` 不要第一天对所有点 N+1 全扫。** Phase 1 只取验收点。以后正式全量同步再分成 Core Sync 和 Detail Enrichment 两阶段，避免最初同步被几千/几万个详情请求拖死。

我建议下一步一次性做完下面这一个“小闭环”。

# 63. Phase 2 后的闸门

Phase 2 通过后：

不要立刻做正式 UI。

下一步应该先做：

```text

```

```text

```

因为最终 Viewer 的详情面板依赖它。

Phase 3 通过以后：

```text
Phase 4 — Offline Viewer
```

这样 UI 一开始拿到的就是完整稳定数据层，而不是边写 UI 边改数据库。

有一个设计决定我尤其建议你现在就采用：**每个 snapshot 自己一份 `core.db`，官方资源全局按 SHA256 去重，用户数据以后另放 `user.db`。** 这会让更新、回滚、断点续传和以后做版本 Diff 都简单很多，比在一个巨大数据库里给所有表塞 `snapshot_id` 干净。

另外，Phase 2 跑完后最值得先看的不是“总共下了多少 GB”，而是三张统计表：**fragment count/size distribution、origin distribution、points outside raster canvas**。Phase 1 已经证明海原市正确；这三组全量统计能最快暴露其他 623 张图里有没有特殊结构。

所以结论很明确：**Phase 2 可以开始，全量下载可以放行。** 这一步仍然只做 Core，不跑全量 `point/info`，也不做正式 Viewer。

可以，**Phase 3 放行**。而且 Phase 2 的结果已经说明一件很关键的事：现在不应该再碰 Core 的结构了，`core.db` 应视为已经冻结的只读产物。

Phase 3 最重要的架构决定，我建议现在就定死：

> **`point/info` 及其图片不写回 `core.db`。**
>
> 为当前 Core Snapshot 建立独立的 `detail.db` / enrichment manifest。未来 Viewer 同时挂载 `core.db + detail.db + user.db`。

这样即使以后详情 API 改 Schema、图片下载失败、重新解析富文本，都不会破坏已经验证通过的 5330 点 Core。

# 13. Raster Bounds

```text

```

因此 raster 像素：

```text

```

```text
(-origin_x, -origin_y)
```

右下角：

```text
(width - origin_x,
 height - origin_y)
```

所以 Leaflet raster bounds 应由：

```text
origin
width
height
```

统一计算。

getRasterBounds(map)

还有一个现在很值得坚持的实现细节：**Viewer 的 Marker 直接用 `[y_pos, x_pos]`，底图通过 `origin` 反推出 Leaflet bounds。** 不要为了“统一成图片像素”而让 Viewer 改用 `raster_x/raster_y`。前者和你已经验证过的官方运行时完全一致，也能让 golden 20 继续保持真正的 0 误差。

另外我暂时**不建议给 624 张图预切本地瓦片**。现在 624 张都是单 raster，先实际测试那 13 张 `8192×8192`。如果浏览器内存和缩放体验确实有问题，再加一个可删除重建的本地 tile cache；否则不要凭想象多造一层 624 张地图的衍生数据。

所以接下来可以按闸门开始 **Phase 4A Viewer Kernel**。4A 的第一个真正验收画面应该非常朴素：**海原市一张官方本地底图 + 48 个真实 marker + 点 5171 能打开本地官方说明/图片 + 20 golden 浏览器坐标仍为 0。** 这过了再做侧栏和漂亮界面。
