可以。基于前面两轮审计和当前状态，我建议不要把后续工作理解成“继续修爬虫”，而是把 **Guide Atlas V3 Closure** 正式拆成几个相互独立、可验收的工程阶段。核心目标是：**先把已发现语料可靠地转化为可审核单元，再压缩 Review backlog，最后建立不会回退的发布闭环。**

# Guide Atlas V3 后续完整规划

## 1. 总体目标

当前系统已经证明三件事：

**架构可运行、Gate 可解锁、Published 可离线消费。**

真正剩下的问题是：

> Source Discovery → Asset Ingestion → Extraction → Matching → Review → Publish → Regression Protection

这条链路目前每一段都存在，但还没有形成一个**可重复、可观测、可恢复、不可静默退化**的生产闭环。

因此最终目标不应该定义成“611/611 全覆盖”，而应拆成两个目标：

### Closure Sprint

达到后正式把 `a1-5` 标记 PASS：

* Gate A/B/C 持续 PASS；
* Published structural error = 0；
* Published hallucinated step = 0；
* Snapshot regression gate 落地；
* 发布流程具备 validate + atomic switch；
* Golden/offline E2E 稳定；
* 工程缺口明确实现或正式 deferred；
* Corpus coverage 不再作为 Closure 阻塞项。

### Corpus Program

Closure 后持续推进：

* 611 targets coverage 持续增长；
* NEEDS_SOURCE 持续下降；
* Review backlog 可控；
* 新 source 可以稳定转化成 publishable guide；
* 每次发布不得破坏已有 coverage。

# 2. 后续路线图

建议按 **P0 → P6** 推进，而不是同时开多个方向。

| Phase | 主题                    | 解决的问题               | 退出条件                    |
| ----- | --------------------- | ------------------- | ----------------------- |
| P0    | Baseline              | 当前状态是否可信            | 全量测试基线明确                |

| P6    | Closure               | a1-5 正式收官           | Closure PASS            |

其中 **P1–P4 是现在真正应该做的主线。**

# 3. P0：建立可信 Baseline

目前存在两个环境：

* 完整开发数据环境：你那里曾跑出 `312 passed`；
* `submit.zip`：缺 `data/current.json` / snapshot DB，不能完整复现。

这需要先正式定义测试层级，否则以后“测试通过”会不断产生歧义。

建议分成：

```text
tests/unit/
tests/integration/
tests/data/
tests/e2e/
```

并定义四种命令：

```text
pytest tests/unit
pytest tests/unit tests/integration
pytest
pytest --run-data-e2e
```

原则是：

**源码包自身必须能够通过 unit + deterministic integration。**

依赖真实数据库的数据测试必须显式标记：

```python
@pytest.mark.data
@pytest.mark.e2e
```

缺数据应该：

```text
SKIPPED: snapshot fixture unavailable
```

而不是 62 个 FAIL。

### P0 验收

要求：

```text
unit/integration: 100% green
data/e2e: 有数据时 green
missing data: skip，不是 fail
```

同时 CI/本地默认：

```bash
python -m pytest
```

必须有明确且稳定的语义。

# 4. P1：Asset Ingestion 正式化

这是当前最高优先级。

现在发现能力已经超过消费能力：

```text
NEEDS_SOURCE     245 → 188
NEEDS_REVIEW     274 → 394
```

继续 discovery 会继续放大 backlog。

所以先解决：

> 已经找到的网页为什么不能成为高质量 Review 输入？

## 4.1 AssetFetcher 抽象

当前已经迈出第一步，下一步建议正式定义：

```python
class AssetFetcher:
    def fetch(
        self,
        asset_url: str,
        page_url: str,
        *,
        refresh: bool = False,
    ) -> AssetFetchResult:
        ...
```

返回值不要只表示 success/failure。

建议：

```python
@dataclass
class AssetFetchResult:
    status: AssetFetchStatus

    source_url: str
    final_url: str | None

    http_status: int | None
    content_type: str | None

    sha256: str | None
    width: int | None
    height: int | None
    format: str | None

    attempts: list[FetchAttempt]
    reason: str | None
```

状态至少：

```text
FETCHED
CACHE_HIT
HTTP_BLOCKED
HTTP_NOT_FOUND
NOT_IMAGE
INVALID_IMAGE
RATE_LIMITED
NETWORK_ERROR
UNSUPPORTED
```

不要再把所有失败压成：

```text
images_in_guide_assets=False
```

因为这个信息量太低。

# 7. P2：修正 QA → Review 边界

这是我认为当前架构中比“图片抓不到”更值得修的地方。

你已经观察到：

> QA_FAIL 页面仍然生成 review item。

这是不理想的。

现在：

```text
crawl
 ↓
extract
 ↓
QA_FAIL ──────────┐
 ↓                 │
review item  ←─────┘
```

应该改成：

```text
crawl
  ↓
extract
  ↓
source QA
  ├── PASS
  │     ↓
  │   matching
  │     ↓
  │   review
  │
  └── FAIL
        ↓
      quarantine
```

也就是说：

> **QA 是 Review 的 admission gate。**

# 11. Signature 的设计

不要只 hash URL。

URL 不是语义 identity。

建议分层。

### Layer 1：Target identity

```text
topic
scope_type
official_target_id
```

例如：

```text
floating_grease|POINT|12345
origami_bird|MAP_LABEL|149
zagreus_hand|POINT_SET|346
```

### Layer 2：Source unit identity

```text
canonical_article_family
page
normalized_heading
image_fingerprint
```

### Layer 3：Review signature

最终：

```python
signature = sha256(
    topic
    + target_key
    + normalized_instruction
    + canonical_asset_hashes
)
```

注意：

**不要让 LLM 生成 signature。**

Signature 必须 deterministic。

# 18. Regression Gate

分三档。

### HARD FAIL

```text
broken asset
missing core target
dangling binding
schema invalid
published target unexpectedly removed
hallucinated step
```

直接阻断。

### COVERAGE FAIL

例如：

```text
floating_grease
37 → 34
```

默认阻断。

```text
origami_bird
43 → 41
```

阻断。

### REVIEW REQUIRED

比如：

```text
guide text changed
image changed
step count changed
```

不一定错误，但需要知道。

# 19. Allowlist / Intentional Regression

有时确实要删除错误攻略。

所以不能规定 coverage 永远只能上涨。

支持：

```yaml
allowed_regressions:
  - topic: floating_grease
    target: point:123
    reason: incorrect binding
    issue: ...
```

没有明确 waiver：

```text
FAIL
```

有 waiver：

```text
PASS_WITH_WAIVER
```

这样才能同时满足：

> 不允许静默退化

和：

> 可以主动修正错误数据。

# 33. 建议的实际实施顺序

接下来不要同时开十个 PR。按下面顺序做：

1. **P1 Asset Pipeline**：真实 3DM/9game smoke matrix → host policy/cache → QA 重跑。
2. **P2 QA admission gate**：QA_FAIL 不再生成 Review，并清理历史污染。
3. **P3 Unit Signature**：canonicalization → signature → evidence merge → 重算 backlog。
4. **P4 Snapshot Regression**：manifest → diff → hard gate → waiver。
5. **Published Audit**：解决 10 个 empty steps，完成 hallucination 全量核验。
6. **P5 Atomic Publish**：staging DB → validation → offline E2E → regression → atomic switch。
7. **Architecture Decisions**：published target / content_block / ArticleFamilyResolver 明确 implemented 或 deferred。
8. **Closure Check + progress.md**：机器验收后正式写 a1-5 PASS。
9. **恢复 Corpus Program**：target-driven discovery。
10. **最后再做 Admin / Resume / Unified AI Cache**。

## 一、先重新定义爬虫 KPI

不要再以 `抓了多少 URL` 为主指标。真正应该优化的是：

$$
\text{有效产出率}
=
\frac{\text{最终形成唯一、QA PASS、可匹配 Review Unit 的页面}}
{\text{实际请求页面数}}
$$

建议每个 topic/host 都统计一条 funnel：

```text
targets NEEDS_SOURCE
    ↓
search queries
    ↓
candidate URLs
    ↓
accepted seeds
    ↓
fetched pages
    ↓
extracted pages
    ↓
QA PASS
    ↓
matched targets
    ↓
unique review units
    ↓
approved
    ↓
published
```

例如以后不再只说：

```text
3DM 抓了 50 页
```

而是：

```text
3DM
candidate URLs       50
canonical pages      31
fetch success        29
asset-complete       24
QA PASS              22
matched              18
unique review units  15
target coverage +12
```

这样才能判断一个站点值不值得继续爬。

# 二、第一优先级：建立 Site Capability Profile

现在 crawler 很容易逐渐变成：

```python
if 3dm:
    ...
elif 9game:
    ...
elif 17173:
    ...
```

这会越来越难维护。

建议增加：

```text
hsrmap/guides/crawler/sites/
    base.py
    generic.py
    profiles.py
```

但不要一上来每站一个复杂 Adapter。

先采用**声明式 SiteProfile**：

```python
SiteProfile(
    domains={"3dmgame.com"},
    canonical_hosts={"www.3dmgame.com"},
    article_patterns=[...],

    pagination=PaginationPolicy(...),
    assets=AssetPolicy(...),
    extraction=ExtractionPolicy(...),

    min_delay=1.0,
)
```

Profile 管的是“规则”，不是反爬绕过。

### Profile 应描述什么

至少六类：

```text
canonical URL
article-family recognition
pagination
asset URL normalization
asset request policy
content extraction hints
```

Generic crawler 负责执行。

这样 80% 网站继续走 generic，只有真正特殊的网站才升级为 adapter。

# 三、URL Canonicalization 要做成爬虫第一公民

你刚修的：

> 手机版/APP 镜像不能作为 sibling page

只是第一层。

真正应该建立：

```python
canonicalize_url(url) -> CanonicalURL
```

处理：

```text
http / https
www.
mobile host
APP host
fragment
tracking query
utm_*
重复 /
尾部 /
canonical link
redirect final URL
```

同时保留：

```text
requested_url
final_url
canonical_url
```

三个概念。

不要覆盖原始 URL。

数据库最好建立：

```text
source_url_alias
----------------
url
canonical_url
reason
discovered_at
```

这样：

```text
www.3dmgame.com/a/123.html
m.3dmgame.com/a/123.html
app.3dmgame.com/a/123.html
```

最终可以归到一个 canonical source。

# 四、Article Family Resolver 值得正式实现了

之前我认为它可以 deferred，但随着 Corpus 扩大，它开始有实际收益。

因为现在至少存在：

```text
article.html
article_2.html
article_3.html
...
```

以及：

```text
desktop mirror
mobile mirror
APP mirror
```

建议抽象：

```python
@dataclass
class ArticleFamily:
    family_id: str
    canonical_url: str
    members: list[ArticlePage]
```

Resolver：

```python
resolve_article_family(url, document)
```

综合：

```text
URL pattern
<link rel=canonical>
title similarity
article ID
prev/next links
pagination links
```

来判断。

这样 pagination 不再是：

> 找几个 URL 再抓。

而变成：

> 扩展一个 Article Family。

这是非常重要的模型升级。

# 六、Priority Frontier

这会明显减少无意义请求。

每个 URL 给 priority：

$$

不用真的搞复杂 ML。


# 十、Image Relevance Filter

这会明显提升 Review 质量。

攻略页可能有 55 张图，但不是 55 张都有用。

可以先用纯规则：

```text
min width
min height
aspect ratio
duplicate SHA
URL pattern
DOM location
```

例如：

```text
header/footer/sidebar
```

里的图直接降低优先级。

然后再做 perceptual hash：

```text
pHash
```

解决：

> 同一张攻略图被重新压缩、加水印、缩放后 SHA 不同。

两层去重：

```text
SHA256 → exact duplicate
pHash  → visual duplicate
```

这对多站转载特别有价值。

# 十三、Retry 必须按失败类型决定

现在很多 crawler 的典型问题是：

```text
失败 → retry 3 次
```

这是不够聪明的。

应该：

```text
404
→ 不 retry

403
→ policy fallback 后停止

429
→ Retry-After / exponential backoff

5xx
→ exponential retry

timeout
→ limited retry

invalid image
→ 不 retry

DNS/transient
→ retry
```

例如：

```text
1s
2s
4s
8s
```

但受：

```text
max attempts
max elapsed time
host policy
```

控制。

# 十四、Rate Limit 应从“固定 1 秒”升级成 Host Scheduler

保留至少 1 秒的友好策略，但调度应该按 host。

例如：

```text
HostQueue
  3dmgame.com
  17173.com
  9game.cn
```

每个 host：

```text
last_request_at
min_interval
backoff_until
consecutive_errors
```

这样未来可以安全地并行：

```text
3DM request
17173 request
9game request
```

同时保证：

```text
同一 host ≥ 1s
```

这比整个 crawler 全局 sleep 1 秒效率高很多。

# 二十三、不要做的几个优化

有几件事看起来“高级”，现在反而不值得：

**第一，不要立即引入 Scrapy 重写。** 现有 pipeline 已经与 Ledger、Review、QA 深度结合，重写框架的收益目前远低于风险。

**第二，不要立即全面 Playwright。** JS rendering 应该是特殊 capability，不是默认抓取方式。

**第三，不要为了 403 无限模拟浏览器。** 如果正常、合规的请求策略仍被明确阻止，应记录 `SOURCE_BLOCKED`，换源比对抗站点更合理。

**第四，不要先做分布式 crawler。** 611 targets 的规模远没到需要 Kafka/Celery crawler cluster 的程度。

**第五，不要继续单纯扩大 seeds。** 当前 Review backlog 已经证明 acquisition throughput 不是唯一瓶颈。
